# G-code Safety Validator Specification

**Document Version:** 1.0.0
**Project:** Sai Rolotech Smart Engines (Roll Forming Engineering Suite)
**Status:** Production-Grade Safety Specification
**Audience:** CNC/controls engineers, backend/API developers, validation-engine developers, QA, safety/compliance reviewers

---

## 1) Purpose

This specification defines the required architecture, data contracts, rule set, diagnostics, and quality gates for the **G-code Safety Validator** used in Sai Rolotech Smart Engines.

The validator is a **safety-critical pre-execution gate** that evaluates generated or imported G-code before it can be classified as CNC-ready, simulated as executable, or exported in manufacturing packages.

This spec is tailored to the Sai Rolotech workflow where roll-forming station outputs, bend sequencing, and machine envelope constraints must be validated deterministically.

---

## 2) Objective

The objective of the G-code Safety Validator is to:

1. Prevent machine collisions and unsafe axis transitions.
2. Enforce deterministic, machine-safe retract behavior.
3. Ensure bend commands are syntactically valid and sequence-consistent with expected process metadata.
4. Guarantee mandatory modal setup (`G21`, `G90`) prior to motion execution.
5. Produce auditable, deterministic diagnostics and a reproducible safety score.
6. Enforce hard-stop policies for critical safety failures.

---

## 3) Scope

### In Scope

- Parsing and validating station-level and multi-station G-code text.
- Safety checks for Z retraction and lateral motion transitions.
- Bend command integrity and direction/count verification.
- Modal setup enforcement for metric and absolute positioning.
- Structured output for UI, API, CLI, audit logs, and CI pipelines.

### Out of Scope

- Real-time PLC interlocks.
- Servo tuning and low-level drive diagnostics.
- Physical machine commissioning procedures.
- Tool wear prediction (informational checks may exist, not safety gates).

---

## 4) Design Principles

1. **Fail-safe by default:** Unknown, malformed, or ambiguous commands shall be treated as unsafe unless explicitly classified as non-motion comments.
2. **Deterministic diagnostics:** Same input must always produce identical issue list ordering and scoring.
3. **Safety over convenience:** Passing format/style checks cannot override critical motion safety failures.
4. **Traceability:** Every issue must map to exact line numbers and stable failure codes.
5. **Separation of concerns:** Parsing, rule evaluation, scoring, and policy gating must be independent pipeline stages.
6. **Manufacturing realism:** Rules align with roll-forming execution patterns including bend direction and retract-before-lateral movement.

  minX: number;
  maxX: number;
  minY: number;
  maxY: number;
  minZ: number;

  safeZClearance: number;

export interface GcodeValidationInput {
  /** Raw G-code program content (UTF-8 text) */
  gcode: string;

  sourceId: string;

  /** Engineering context used for deterministic safety checks */
  station: StationContext;

  /** Machine constraints and safe travel envelope */
  machineEnvelope: MachineEnvelope;

  /** Expected bend sequence generated by tooling pipeline */

### Input Requirements

- `gcode` must be non-empty after trimming comments/whitespace.
- `expectedBends` is required for bend count/direction validation.
- `machineEnvelope.safeZClearance` must be valid numeric value and within `[minZ, maxZ]`.
- Units and coordinate mode assumptions are not allowed; they must be validated from commands.

## 7) Severity Model

- **critical**
  - Immediate safety risk, invalid motion state, or mandatory rule violation.
  - Any critical issue forces `isValid = false` and `isCncReady = false`.
- **warning**
  - Potential risk or process-quality concern; non-blocking unless `strictMode=true` and policy escalates.
- **info**
  - Non-blocking diagnostics and trace data.

Severity assignment is rule-defined and must not be inferred heuristically at runtime.

## 8) Required Safety Rules

### 8.1 Required Safe Z Calculation

**Definition:**

`requiredSafeZ = max(machineEnvelope.safeZClearance, currentBendTopZ + retractMargin)`

Where:
- `retractMargin` is a machine-configured constant (default: `2.0 mm` unless overridden by station config).
- `currentBendTopZ` is highest known engagement reference during active bend phase.

If `currentBendTopZ` cannot be resolved, fallback:

`requiredSafeZ = machineEnvelope.safeZClearance`

Validator must expose `safeZRequired` in output summary.

### 8.2 Unsafe Lateral Move Rule

A lateral move (`X` and/or `Y` change) is unsafe if current `Z < requiredSafeZ` immediately before executing that lateral move.

- **Failure Code:** `UNSAFE_LATERAL_MOVE`
- **Severity:** `critical`
- **Trigger:** Any feed/rapid lateral transition while below safe retract plane.

### 8.3 Safe Retract Rule

Before any lateral move that changes bend position or station-relative tooling position, a retract to `Z >= requiredSafeZ` must be present in deterministic command order.

- **Failure Code:** `MISSING_SAFE_RETRACT`
- **Severity:** `critical`
- **Trigger:** Missing explicit retract transition preceding lateral move.

### 8.4 Bend Command Rule

Bend commands must be syntactically valid and sequence-consistent with expected bend metadata.

- **Failure Code:** `MALFORMED_BEND_COMMAND`
  - Invalid bend command tokenization or missing required parameters.
  - **Severity:** `critical`

- **Failure Code:** `BEND_DIRECTION_MISMATCH`
  - Parsed bend direction does not match `expectedBends[index].direction`.
  - **Severity:** `critical`

- **Failure Code:** `BEND_COUNT_MISMATCH`
  - Number of parsed bend commands differs from expected bend count.
  - **Severity:** `critical`

### 8.5 Final Retract Rule

Program end must leave tool in safe clearance state.

- **Failure Code:** `MISSING_FINAL_RETRACT`
- **Severity:** `critical`
- **Trigger:** Final executable motion ends with `Z < requiredSafeZ` or no final retract command exists.

### 8.6 Modal Setup Rule

Prior to first executable motion command, program must explicitly set:

- Metric mode: `G21`
  - **Failure Code:** `MISSING_METRIC_MODE`
  - **Severity:** `critical`

- Absolute positioning mode: `G90`
  - **Failure Code:** `MISSING_ABSOLUTE_MODE`
  - **Severity:** `critical`

Modal inference from machine defaults is prohibited.

## 9) Parse Model

### Supported Command Families

1. **Modal setup:** `G21`, `G90`, `G91`.
2. **Motion commands:** `G0/G00`, `G1/G01` with axes `X`, `Y`, `Z` and feed `F`.
3. **Bend commands:** project-defined bend opcodes (e.g., `BEND`, `M700` depending machine post-processor profile).
4. **Program controls:** `M2`, `M30`.
5. **Comments:** `; comment` and `(comment)`.

### Parsed State

Parser/validator state must track at minimum:

- `lineNumber`
- `metricMode: boolean`
- `absoluteMode: boolean`
- `currentPosition: { x?: number; y?: number; z?: number }`
- `requiredSafeZ: number`
- `lastRetractLine?: number`
- `bendIndex: number`
- `parsedBendDirections: BendDirection[]`
- `hasFinalRetract: boolean`
- `hasProgramEnd: boolean`

```ts

  motion: "G0" | "G00" | "G1" | "G01";

  y?: number;
  z?: number;
  f?: number;

  type: "bend";
  opcode: string;
  direction: "UP" | "DOWN";
  angleDeg?: number;
  bendIndex?: number;
}

export interface ParsedProgramEnd extends ParsedBase {
  type: "programEnd";
  code: "M2" | "M30";
}

export interface ParsedComment extends ParsedBase {
  type: "comment";
  text: string;
}

export interface ParsedUnknown extends ParsedBase {
  type: "unknown";
  token: string;
}

export type ParsedCommand =
  | ParsedModalCommand
  | ParsedMotionCommand
  | ParsedBendCommand
  | ParsedProgramEnd
  | ParsedComment
  | ParsedUnknown;
```

## 11) Validation Pipeline

1. **Preflight Input Validation**
   - Validate non-empty G-code and required metadata.
2. **Lex + Parse**
   - Convert text lines to `ParsedCommand[]` with stable line references.
3. **Syntax Validation**
   - Emit malformed/unknown command issues.
4. **Mode Validation**
   - Enforce `G21` and `G90` before first motion.
5. **Transition Safety Validation**
   - Evaluate retract and lateral movement safety (`Z` vs `requiredSafeZ`).
6. **Bend Sequence Validation**
   - Validate bend syntax, direction, and count consistency.
7. **Final State Validation**
   - Enforce final retract and safe end state.
8. **Deterministic Diagnostics + Scoring**
   - Sort issues by `(line, severityRank, code)` and compute final score.
9. **Policy Gate**
   - Set `isCncReady` only if all hard-fail conditions pass and score threshold met.

---

## 12) Required Checks

### A) Syntax Checks
- Command family identification.
- Numeric parameter parsing and finite-value validation.
- Bend opcode structure validation.

### B) Mode Checks
- `G21` and `G90` present before first motion.
- Reject implicit or late modal setup.

### C) Transition Safety Checks
- Lateral move below safe retract plane.
- Missing retract before lateral position changes.
- Envelope bound checks (recommended warning/critical by policy).

### D) Bend Sequence Checks
- Malformed bend syntax.
- Bend direction mismatch against station expectation.
- Bend count mismatch with planned sequence.

### E) Final State Checks
- Final retract to safe Z.
- Safe end program state prior to `M2/M30`.

### F) Deterministic Diagnostics
- Stable issue ordering.
- Stable score for identical inputs.
- Stable failure codes independent of runtime environment.

## 13) Required Failure Codes

Minimum mandatory failure code registry:

- `UNSAFE_LATERAL_MOVE`
- `MISSING_SAFE_RETRACT`
- `MALFORMED_BEND_COMMAND`
- `BEND_DIRECTION_MISMATCH`
- `BEND_COUNT_MISMATCH`
- `MISSING_FINAL_RETRACT`
- `MISSING_METRIC_MODE`
- `MISSING_ABSOLUTE_MODE`

Recommended additional codes for robustness:

- `UNKNOWN_COMMAND`
- `INVALID_NUMERIC_VALUE`
- `OUT_OF_MACHINE_ENVELOPE`
- `MISSING_PROGRAM_END`

Failure code strings must be treated as API contracts and versioned carefully.

## 16) Required Test Coverage

Minimum test suites:

1. **Parser Unit Tests**
   - Modal, motion, bend, comments, unknowns, malformed numerics.
2. **Rule Unit Tests (per failure code)**
   - One positive and one negative case per required failure code.
3. **Sequence Property Tests**
   - Determinism across repeated runs and shuffled non-semantic comments.
4. **Integration Tests**
   - Full program validation with realistic roll-forming station samples.
5. **Regression Tests**
   - Previously observed unsafe trajectories and bend mismatches.
6. **Strict Mode Tests**
   - Warning escalation policy behavior in CI.

Coverage targets (minimum):

- Line coverage: **>= 90%**
- Branch coverage: **>= 85%**
- Failure code path coverage: **100%** for required failure codes

## 17) CI Integration Requirements

1. Validator must run in CI for every PR touching:
   - G-code generation, post-processing, or validation modules.
   - Station export/package generation.
2. CI must execute:
   - Unit tests.
   - Integration fixtures.
   - Determinism replay checks.
3. Build must fail when:
   - Any validator test fails.
   - Required failure code registry changes without version bump and changelog entry.
4. CI artifacts must include:
   - Machine-readable validation report JSON.
   - Human-readable summary with failure code histogram.

## 18) CLI Behavior

Recommended command:

```bash
pnpm gcode:validate --input ./fixtures/station-04.gcode --station ST-04 --json
```

Required CLI behavior:

- Exit code `0` only when `isValid=true` and no hard-fail conditions.
- Exit code `2` for validation failures (safety or syntax).
- Exit code `3` for internal/runtime validator errors.
- `--json` prints only serialized `GcodeValidationResult`.
- `--strict` enables warning escalation policy.
- CLI output must be deterministic for identical inputs.

---

## 19) Quality Gates

A program may be marked **CNC-ready** only when all gates pass:

1. `critical issue count == 0`
2. Required modal setup checks pass (`G21`, `G90`)
3. All retract and lateral safety checks pass
4. Bend direction/count checks pass
5. Final retract rule passes
6. `safetyScore >= 70`

If any gate fails, CNC-ready classification is denied.

---

## 20) Hard Fail Policy

The following conditions are **non-overridable hard fails**:

- Any issue with severity `critical`.
- Missing modal setup (`MISSING_METRIC_MODE`, `MISSING_ABSOLUTE_MODE`).
- Unsafe transition faults (`UNSAFE_LATERAL_MOVE`, `MISSING_SAFE_RETRACT`).
- Bend integrity faults (`MALFORMED_BEND_COMMAND`, `BEND_DIRECTION_MISMATCH`, `BEND_COUNT_MISMATCH`).
- Missing safe terminal state (`MISSING_FINAL_RETRACT`).

Hard fail policy applies across API, UI, export pipeline, and CLI.

---

## 21) Final Policy Statement

In Sai Rolotech Smart Engines, G-code is considered **non-executable by policy** until the G-code Safety Validator passes all mandatory rules and quality gates.

No UI success state, no export success state, and no CNC-ready label may be presented for synthesized, partial, blocked, malformed, or unsafe programs. For manufacturing safety, this validator is the authoritative pre-execution gate and must be treated as a release-blocking control in production.

## Audit Mapping (Required)

### Bug / Risk Class Addressed

- **Primary risk:** Unsafe axis transitions and incorrect bend execution can cause tooling collision, part scrap, or machine damage.
- **Secondary risk:** Missing modal setup can reinterpret coordinates/units and produce hazardous motion.

### Fix Defined by This Specification

- Introduces strict, deterministic contracts for parser behavior, safety checks, failure codes, and CNC-ready policy gating.
- Codifies mandatory retract, lateral move, bend validation, and final safe state rules.

### Remaining Risks

- Post-processor variants may introduce new bend opcode formats requiring parser profile updates.
- Machine-specific retract margins may need calibration; defaults must not be assumed universally safe.
- Real-time PLC interlocks remain outside validator scope and must independently enforce safety.

### 8 Audit Buckets Impacted

- **5. Export engine (ZIP, CSV, XML, DXF):** blocks export of unsafe G-code packages.
- **7. G-code / CNC safety:** primary bucket; defines validator policy and required failure handling.
- **4. Roll tooling engine (indirect):** bend sequence expectations consumed from tooling outputs.
